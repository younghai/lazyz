# 플레이북

각 플레이북의 단계를 todo 목록 앞에 그대로 복사한다. 하지 않는 단계는 `건너뜀: <이유>`와 함께 남긴다. 모든 플레이북의 마지막 산출물은 (1) 검증 증거, (2) 원칙을 인용한 대답이다.

## investigation — 읽기 전용 질문

"어떻게 돌아가?", "왜 이렇게 만들었어?", "확실해?", "X해야 할까?" 같은 질문. 답이 코드 밖(역사·논의·이슈)에 있을 수 있다.

1. 질문을 한 문장으로 다시 쓴다. 답이 사실인지 판단인지 표시한다.
2. 코드 닻을 잡는다 — 파일·줄, 심볼, 관련 커밋/PR. 모든 주장에 이 닻이 붙는다.
3. 증거 원천별로 나눠 조사한다 — 코드/테스트, 저장소 역사(git log, blame), 이슈·문서, 실행 관찰(재현). 원천이 없으면 "없음"도 기록한다.
4. 출처를 단 답을 쓴다. 각 주장에 file:line, 커밋, 재현 결과를 붙인다. 추측은 추측이라고 쓴다.
5. 답을 바꿀 수 있는 가장 싼 확인 하나를 제안한다.

## bug-fix — 재현 → 원인 → 수정 → 검증

1. **재현 먼저.** 실패하는 테스트나 재현 스크립트를 만든다. 재현 못 하면 원인을 찾은 게 아니다.
2. 재현이 고장 낸 지점을 따라간다. 증상이 처음 잘못되기 시작한 곳을 찾는다. 그곳이 아닌 곳에 가드를 넣는 건 수정이 아니다.
3. 같은 전제를 공유한 수정 2개가 같은 게이트에서 실패했으면 전제 자체를 적어서 검사한다.
4. 가장 작은 수정을 한다. 데이터 구조가 원인이면 논리가 아니라 구조를 고친다.
5. 재현 스크립트/테스트가 통과하는지, 관련 테스트 전체가 깨지지 않는지 확인한다.
6. 같은 실수를 다른 곳에서 할 수 있는지 grep하고, 반복 가능성이 있으면 구조로 막는다(lint·타입·가드).

## feature — 데이터 형태에서 시작

1. 요청을 사용자가 관찰할 행동으로 쓴다. 완료 조건을 검사 가능하게 만든다.
2. **데이터 형태부터 이름 붙인다.** 상태·입력·출력의 모양이 코드의 나머지를 결정한다.
3. 경계를 정한다 — 파싱·검증은 경계에서, 내부는 순수하게. 불법 상태를 타입으로 표현 못 하게 한다.
4. 구현은 가장 작은 단위로 나누고, 각 단계가 끝날 때 확인 가능한 상태가 되게 순서를 잡는다.
5. 실행으로 증명한다 — 실제 경로를 구동하고 결과 상태를 관찰한다. 내부 세터·테스트 전용 경로가 아니라.
6. 부작용(파일·행·메시지)도 화면과 함께 확인한다.

## refactoring — 행동 보존

1. 변경 전 상태를 증명 가능하게 둔다 — 테스트, 스냅샷, 픽스처. 없으면 먼저 만든다.
2. 제거 먼저 — 죽은 코드, 중복 검증, 한 번 호출하는 래퍼.
3. 한 단계는 하나의 모양 변경. 각 단계 후 전체 확인.
4. 새 내부 API를 만들면 같은 변에 호출자를 전부 옮기고 구 API를 삭제한다. 호환 레이어를 남기지 않는다.
5. 끝에 행동이 같음을 증명한다 — 변경 전 증거와 대조.

## perf-issue — 측정 대비 개선

1. **먼저 측정.** baseline 없이 개선하지 않는다. 무엇을 재는지(샘플 수, 1샘플의 정의, 순서)를 기록한다.
2. 프로파일·추적·계측으로 병목을 찾는다. 추측으로 최적화하지 않는다.
3. 개선 후 같은 방법으로 다시 잰다. 개선 전후 수치와 측정 조건을 함께 보고한다.
4. 숫자를 설명한다 — 무엇이 제한했는지, 재 측정이 다른 걸 잰 건 아닌지(에러, 워밍업, 캐시).
5. 승인된 개선마다 커밋 1개. 효과 없는 변경은 버린다.

## hillclimb — 한 지표의 지속 개선

perf-issue가 일회성이라면 이건 지속 루프다.

1. 지표와 목표를 검사 가능하게 정의한다.
2. 가설 → 변경 → before/after 측정 → 판정. 승인마다 커밋 1개, 기각은 버린다.
3. 정체되면 피벗하거나 멈춘다. 목표를 몰래 낮춰 성공 선언하지 않는다.
4. 매 이터레이션을 결정 로그에 한 줄 남긴다.

## prototype — 관찰로 결정

1. 갈림길을 적는다 — 무엇을 결정하려는가.
2. 갈림길을 가르는 가장 싼 관찰이 무엇인지 설계한다. 버릴 코드임을 명시한다.
3. 프로토타입 2~3개를 만들어 나란히 놓고 관찰한다. 하나면 비교 대상이 없다.
4. 결과로 결정하고, 결정과 근거를 한 문장씩 기록한다. 프로토타입은 버린다.

## runtime-forensics — 실행 중 증상의 계측 진단

**진단이 산출물이다. 소스에서 이론화하지 않고 살아 있는 프로세스를 계측한다.** 수정은 요청받았을 때만 한다. lazyz:debugging 스킬과 함께 쓸 수 있다.

1. 매칭되는 표면에서 살아 있는 신호를 캡처한다 — 도는 프로세스의 CPU 프로파일, 릭의 힙 스냅샷, 화면 글리치의 트레이스. 추측이 아니라 실제 아티팩트.
2. 아티팩트를 범인으로 환원한다 — 핫패스의 함수, 릭 객체에서 GC 루트까지의 retainer 체인, 입력 없이 도는 루프. 큰 아티팩트는 서브에이전트에서 파싱하고(guard-the-context-window 원칙) 환원된 결과만 메인에 남긴다.
3. 믿기 전에 메커니즘을 증명한다. 실행 중 프로세스에 계측을 심거나, 리로드 없이 라이브 코드를 핫픽스해 가설을 싸게 확인한다.
4. 발견을 소스에 대응시킨다 — 파일, 심볼, 할당·스케줄하는 줄.
5. 산출물: 캡처한 신호, 환원된 발견, 증명 방법, 소스 위치, 아티팩트 경로. 원인이 알려지면 bug-fix 또는 perf-issue로 넘긴다.

## trace-forensics — 캡처된 아티팩트 진단

**아티팩트가 이미 존재한다. 다시 실행하지 말고 읽는다.** runtime-forensics가 살아 있는 프로세스를 계측한다면, 여기선 캡처가 고정된 데이터셋이다.

1. 포맷을 식별하고 맞는 도구로 적재한다 — cpuprofile/`.json.gz`는 트레이스 파서, spindump는 텍스트, heapsnapshot은 힙 도구. 큰 아티팩트는 서브에이전트에서 파싱하고 환원된 결과만 메인에 남긴다.
2. 원시 아티팩트를 질의 가능한 형태로 바꾼다 — 샘플·프레임·노드마다 한 줄씩 sqlite에 덤프. 읽기 전에 질의 가능한 모양에 먼저 도달한다.
3. 원인으로 좁힌다 — 가장 시간을 많이 잡은 프레임과 핫패스까지의 호출 트리, 릭이면 retainer 체인, spindump면 on-CPU에 갇히거나 블록된 스레드와 대기 사유.
4. 소스로 귀속한다. 심볼 없는 프레임은 진단이 아니다 — 심볼을 해석하거나, 아티팩트가 심볼을 안 싣는다고 솔직히 말한다.
5. 짝 캡처(before/after)가 있으면 diff로 확인한다. 없으면 아티팩트가 지지하는 가장 강한 가설이라고 표시하고 확정이라고 하지 않는다.
6. 산출물: 아티팩트와 포맷, 환원된 발견, 소스 위치, 경로, 짝 캡처 여부. 수정은 요청받았을 때만.

## visual-parity — 픽셀 일치 이관

**baseline이 spec이다. baseline을 건드리지 않는다.** 눈이 아니라 이미지 diff로 검증한다.

1. 이관 전에 baseline을 먼저 만든다 — 현재 컴포넌트를 상태별로 캡처하는 시각 회귀 하네스. 두 구현을 맞출 때는 대상도 캡처한다. baseline 없이 parity 주장 없다. 후속 작업이 아니라 차단 전제다.
2. 지름길 금지 조항을 밝히고 지킨다 — 하네스 수정 금지, baseline 변조 금지, diff를 통과시키려는 컴포넌트 구조 재배치 금지. baseline이 틀려 보이면 고치지 말고 물어본다.
3. 한 번에 컴포넌트 하나. 공유 프리미티브를 차단 단계로 먼저 이관한다.
4. 컴포넌트마다 매칭되는 표면에서 이미지 diff로 검증한다(lazyz:visual-qa의 diff 도구). 0이 아닌 diff는 실패다. 픽셀 차이를 조사한다.
5. 산출물: 이관한 컴포넌트, 각각의 diff 결과, baseline 하네스 위치, 남은 것.

## multi-phase-plan — 단계별 증거 계획

**계획이 산출물이다. 코드가 아니다.** 소유자가 칸마다 실행하고 사용자가 증거로 감사하는 체크리스트. 구현하지 않는다.

1. 변경이 한두 파일에 방법이 명백하면 계획을 건너뛴다. 그렇게 말하고 멈춘다.
2. 열린 질문은 계획을 쓰기 전에 prototype 플레이북으로 정리한다. 브랜치·SHA·스크린샷을 부록에 남긴다. 실행으로 못 정하는 제품·취향 결정만 사용자에게 옵션과 함께 묻는다.
3. 탐색은 서브에이전트로 한다 — 파일 포인터, 관례, 테스트 명령, 진입점만 돌려받고 덤프는 받지 않는다(guard-the-context-window).
4. 계획 파일을 쓴다. 한 섹션에 하나의 단위(PR), 각 단위는 자체 증거를 갖는다(sequence-verifiable-units). 각 단위마다: 다루는 파일 / 하는 변경 / 관찰되는 결과 / 검증 방법(사용자 검증 정책에 맞게 실행 시점 명시). 부록: 프로토타입 증거, 기각한 대안, 위험.
5. 계획 경로와 요약(단위·의존성·검증되지 않은 것)을 돌려주고 멈춘다. 실행은 사용자의 명시적 go와 그 시점의 승인 검증으로 시작한다.

## overnight — 자율 실행 계약

사람이 자리를 비기는 작업. 계약 없이 시작하지 않는다.

계약서 양식:

```text
목표: <한 문장>
완료 조건(done means): <실행해 통과/실패를 가리는 조건들>
작업 공간: <새 브랜치/워크트리, 기준 커밋>
권한: 커밋 전에 묻지 않는다. <항상 멈춤 목록은 그대로>
결정 로그: decisions.tsv에 한 줄씩 (decision-log 스킬)
탈출구: <N>시간 안 풀리면 멈추고 이유를 기록한다
```

루프:

1. 완료 조건을 확인한다.
2. 가장 작은 정당화된 변경을 하나 한다.
3. 실제 아티팩트로 검증한다.
4. 진전이 있으면 커밋, 없으면 버린다.
5. 결정 로그에 한 줄 남긴다.
6. 1로 돌아간다. 막힘이 탈출조건에 닿으면 멈추고 이유를 쓴다.

돌아온 사람에게는 Attention 리뷰부터 보여준다(decision-log 스킬의 감사 절차).

## pause-safely / session-pickup — 멈추고 이어받기

pause-safely:

1. 현재 단계를 끝내거나 안전하게 되돌린다. 반쯤 된 상태를 남기지 않는다.
2. 진행 체크포인트를 커밋한다(WIP 표시).
3. 이어받기 메모를 쓴다 — 목표, 완료 조건, 여기까지 한 것, 다음 한 단계, 막힌 것.
4. 결정 로그가 있으면 마지막 줄로 상태를 남긴다.

session-pickup:

1. 이어받기 메모·결정 로그·브랜치·커밋을 읽는다. 요약을 믿지 말고 실제 상태(테스트, git)로 확인한다.
2. 새 세션은 통합 브리프(원래 요청 + 이후 지시 + 이전 기록)로 시작한다. 대화를 이어받지 않고 새로 시작하면 지시가 묻힌다.
3. 완료 조건을 재확인하고 루프를 계속한다.

## pr-briefing — 커밋·PR 작성 (사용자 요청 시)

**사용자가 커밋·PR을 명시적으로 요청했을 때만 실행한다.** 요청이 없으면 작업 결과 보고로 끝낸다.

커밋:

1. 커밋은 자유롭게 쌓고, PR을 열기 전에 작고 순서 있는 커밋으로 정리한다(rebase). 각 커밋이 따로 landable해야 하고, 순서가 이야기를 말한다.
2. 방금 만든 커밋에 속하는 수정은 amend, 분리 가능하면 새 커밋. 커밋 본문은 제목을 반복하지 않는다.
3. 제목은 Conventional Commits — `type(scope): subject`, 끝에 마침표 없음. type은 `feat`/`fix`/`docs`/`refactor`/`test`/`chore`/`perf` 등. subject는 짧은 명령형이고, 변경을 대표하는 실제 심볼이 있으면 이름 붙인다. 예: `fix(pstack): retarget opening-a-pr babysit trigger`.

PR 본문 — 리뷰어가 diff를 가진 사람을 위한 1분 브리핑. 짧고 단순한 문장. 이 순서의 `##` 소제목, 말할 게 없는 섹션은 뺀다:

- `## Why`: 문제와 접근, 1~3문장. SHA·리베이스 계보·"main 기반이다" 서론 없음.
- `## What changed`: 1~3 불릿. 변경을 대표하는 심볼·경로만. 이름이 바뀌면 양쪽 다 이름 붙인다.
- `## Scope`: 항상. 무엇을 다루고 무엇을 의도적으로 뺐는지 1~3항목.
- `## Tradeoffs`: 리뷰어가 그냥 물을 만한 기각된 대안만.
- `## Blast Radius`: 누구·무엇을 건드리는지, 왜 안전(또는 위험)한지 1~2문장.
- `## Verification`: 실제 실행 경로와 결과 1~3 불릿. 성능이면 주 수치 하나(단위, before → after). 방법론 나열은 링크된 아티팩트로.

크기·스택: 큰 PR 하나보다 좁은 PR 여럿. 스택은 자식이 부모 팁에 rebase하고 부모 브랜치를 타깃으로 한다. 주장을 증명하는 스크린샷·영상만 본문에 붙인다.
