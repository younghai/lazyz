# How

서브시스템의 **실행 동작**을 해부한다. 호출 경로, 상태 전이, 실패 경로, 부작용. 설계 사유는 다루지 않는다(그건 why). 사용자가 물어본 소비자 시점에서 설명한다.

출처: cursor/plugins pstack v0.15.25 (MIT, poteto)의 how 스킬을 ZCode 환경으로 축소 포팅.

## 절차

1. **범위 고정.** 질문에서 서브시스템 경계를 정한다("취소는 어떻게 돼?" → 취소 진입점부터 상태 반영까지). 저장소 전체 해부로 번지지 않는다.
2. **들여다보기 전에 먼저 예측을 한 줄 적는다.** 이름·구조만 보고 "아마 이럴 것"이라고. 나중에 예측이 빗나간 곳이 설명에서 가장 가치 있는 부분이다.
3. **실제 코드를 읽는다.** 진입점(라우트·핸들러·이벤트) → 데이터 흐름 → 상태 저장 → 부작용(PUT/파일/외부 호출) 순서로. 대형 저장소면 읽기 전용 Agent(Explore)로 넓게 훑고 핵심 경로만 직접 읽는다.
4. **실행으로 확인한다.** 정적 읽기만으로 답하면 "읽은 대로"일 뿐이다. 될 수 있으면 실제로 구동하거나 기존 테스트를 돌려서 주장하는 동작이 관찰되는지 확인한다. 특히 "n+1 있어?" 같은 질문은 읽기 + 실행(로그·카운트) 둘 다. 실행이 불가능하면 어디까지가 읽기 기반인지 밝힌다.
5. **해부 설명 작성.** 아래 계약대로.

## 설명 계약

- **한 문장 요약.** 시스템이 무엇을 보장하는지.
- **주요 경로.** 사용자 액션 → 결과까지의 단계. 파일:줄 인용.
- **상태.** 누가 어떤 상태를 소유하고 어디서 바뀌는지. 숨은 상태(메모리 캐시·모듈 스코프·디바운스 타이머)를 명시적으로 드러낸다.
- **실패 경로.** 에러가 어디서 잡히고 무시되고 전파되는지.
- **예측이 빗나간 곳.** 2단계에서 틀린 예측. 독자가 같은 착각을 할 곳이다.
- **주의점.** 이 서브시스템을 변경할 때 알아야 하는 것(불변식, 순서 강제, 상호작용).

인용은 전부 실제 파일:줄. 실행으로 확인한 부분과 읽기만 한 부분을 구분해 표시한다.

**응답:** 위 계약의 해부 브리프. 요약 먼저, 그다음 경로·상태·실패·주의점.
