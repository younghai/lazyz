LazyZ는 ZCode 안에서 실행되는 로컬 코딩 작업 도구다. 웹/API/DB 서버는 없다. 12개 패키지형 component가 시작 상태, 규칙, 코드 탐색, 실행 증거, 재개, 목표 상태를 나눠 담당한다. 별도 Xcode 제품은 건드리지 않았다.

입력 → 처리 → 결과 → 사람 검토

사용자 요청·코드·기존 이력→ AI가 맥락을 읽고 계획·도구 사용→ 작업별 결과·증거·보고서→ 사람이 승인 범위와 결과 검토

모델은 제공된 맥락을 바탕으로 계획과 도구 호출을 제안하고 결과를 해석한다. 호스트 도구가 파일/프로세스를 처리한다. 이 그림은 관찰된 입출력 흐름이며 모델 내부 사고를 관찰한 것이 아니다. 계획 승인, 외부 게시 권한, 결과 적합성은 서로 다른 판단이다.

우선 해결할 기존 과제

  1. /start-work 계약 정리: SubagentStop, 수동 Boulder 작성, 계획이 없을 때 실행 안내가 현재 ulw-execute 계약과 어긋난다. 이번에는 권장 진입점과 한계를 문서화했으며 runtime workflow를 새로 고치지는 않았다.
  2. 실제 호스트 확인: 작은 승인된 과제로 설치 발견→계획→실행→실패→재개를 확인해야 공개 운영 주장을 할 수 있다.
  3. 상태 일관성: 모델 작성 Boulder/ledger와 versioned goals의 작성 경계·전이 규칙을 통일할 필요가 있다.
  4. 측정 범위: Agent 호출 예산은 모든 내부 API/토큰 비용 예산이 아니다. 호출 수·시간·읽은 바이트를 먼저 측정한 뒤 성능 개선해야 한다.
  5. 신뢰와 재개 한계: 해시는 신뢰 실행 증명이 아니고 Stop은 최대 3회 연속 재개다. 압축 뒤 자동 복구도 보장되지 않는다.

이 과제들은 대부분 기존 설계·문서 한계다. 이번 정리로 새로 보안이 완성되거나 업무 시간이 단축됐다고 결론내리지 않는다.

장기 업무 배분과 재사용 후보

반복 업무 60% / 기존 방법 개선 30% / 새로운 실험 10%를 장기 포트폴리오로 제안한다. 이번 작업 할당량이나 실제 시간 비율이 아니며, 실제 배분은 미측정이다.

반복 후보는 공개용 소스 비교와 문서 현황 정리, 방법 개선 후보는 상태 소유권·호환 문구 정리, 실험 후보는 호출·시간·바이트 계량을 붙인 작은 ZCode 과제다. 효과는 추정이며 자동 설치/배포/유료 실험을 시작하지 않았다.

재사용 후보의 흐름: 개발 입력 고정 → dry-run → 사람이 변경/공개 범위 검토 → apply와 백업 → 허용된 검사 → 별도 게시 승인. 경로/버전 불일치·동시 소스 변경·symlink 발견 시 중단한다. 이번 실제 사용 근거는 있으나 범용 성공 workflow 인증은 아직 없다.
