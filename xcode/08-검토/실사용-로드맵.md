## 1주차 — dogfooding

### 하네스

`scripts/dogfood.sh` — xcode 로 xcode 를 고치게 하고 **우리가** 판정한다.

- 실제 저장소는 절대 건드리지 않는다. `rsync` 로 임시 사본을 만들고 거기서만 돈다.
- 사본이 **처음부터 초록**인지 먼저 확인한다 — 아니면 그 실행은 무의미하다.
- 판정은 에이전트의 자기 보고가 아니라 사본의 `check.sh` · `test.sh` 로 한다.

벤치와 같은 규율이다: 픽스처는 파일 5개짜리 장난감이고, 실제 저장소는 64파일 13,000줄에
상호참조·타입검사·테스트 202건이 얽혀 있다. **픽스처가 만들 수 없는 실패가 여기서 나온다.**

### 실행 3건 — 무엇이 드러났나

| # | 태스크 | 1차 결과 | 드러난 것 |
|---|---|---|---|
| 1 | tokens.ts 오타 확인(읽기만) | 아무것도 안 바꿈 ✓ | 정상 — 할 게 없으면 안 한다 |
| 2 | `find` 툴 추가 | **바꿨지만 빨감** | 형식 오류로 `check.sh` 실패 (F1) |
| 3 | debounce 유틸 추가 | **초록** (F1 수정 후) | 수정이 실효 확인 |

### F1 — 에이전트가 자기 형식 오류를 못 잡는다 (수정 완료)

실행 2에서 xcode 가 완전한 글롭 엔진 + 툴 11테스트를 만들었다. **코드는 돌고 테스트도
202건 통과**했는데 `biome` 형식 검사에서 멈췄다. 사람이 `biome --write` 한 번 돌려야
초록이 됐다.

근본 원인은 우리 아키텍처의 구멍이었다:

- 시스템 프롬프트가 *"작업이 끝나면 **테스트로** 검증한다"* 라고만 했다.
- 에이전트는 프로젝트에 lint·타입 검사가 **있다는 사실 자체를** 알 방법이 없었다.
- 그래서 "코드가 돈다"에서 멈추고, "프로젝트 기준을 통과한다"까지 가지 않았다.

**수정** — 시스템 프롬프트를 바꿨다:

> 작업이 끝나면 검증한다. 테스트만이 아니다 — 그 프로젝트가 쓰는 검사를 전부 통과해야
> 한다. package.json 의 scripts(test·lint·check·typecheck)나 CONTRIBUTING·AGENTS 문서를
> 먼저 보고, 있으면 그 명령을 돌려 초록인지 확인한 뒤에 끝낸다.

**재현으로 확인** — 같은 종류의 태스크(실행 3)를 다시 돌렸더니 에이전트가 스스로
`biome` · `tsc` · 구조규칙 · 테스트를 전부 돌리고 초록을 확인한 뒤 끝냈다. 사람 손 0.

이것이 dogfooding 의 값어치다. 벤치 픽스처(`node check.mjs` 하나)에는 lint 단계가
없어서 이 구멍이 영원히 안 보였다.

### F2 — 완료한 계획 항목이 "남은 일"로 남는다 (수정 완료)

실행 2의 로그에서 계획은 `4/4 완료`인데 워킹 메모리는 `남은 일 4` 였다.

원인: `afterExecute` 가 상태를 갱신한 `updated` 계획을 만들어 이벤트로는 내보내면서,
워킹 메모리에는 **원본 `plan`** 을 넘기고 있었다. nextSteps 필터가 갱신 전 상태를 봐서
다 끝낸 항목이 그대로 남았다. 재개하면 "할 일 4개 남음"으로 이어받는 거짓말이 된다.

**수정** — `updateWorkingMemory` 에 `updated` 를 넘긴다. 계획이 없으면 `null`.

## 2주차 — 결함 5건, 그중 하나는 보안

dogfooding 을 성격이 다른 태스크로 확장했다: 패키지 경계를 넘는 기능(A) · 동작 불변
리팩토링(B) · 버그 사냥(C). B 는 한 번에 초록, A 와 C 는 형식에서 걸렸다.

### F3 — max-turns 가 실제 크기 태스크에 부족하다

A 태스크가 30턴을 다 쓰고도 못 닫았다. dogfood 는 50 으로 올렸다.
`Agent` 기본값 20 은 실사용 기준 재검토 대상 — 다만 A 는 50 에서도 실패했으므로
**턴 부족은 원인이 아니라 증상이었다.**

### F4 — 다중 파일 타입 정합을 못 맞춘다 (구조로 해결)

A 태스크(5파일에 걸친 필드 추가)를 세 번 돌렸는데 매번 타입 오류가 남았다.
세션 로그를 보니 에이전트는 `check.sh` 와 `tsc` 를 **여덟 번 돌렸다.** 오류를 보고도
못 닫았고, 마지막엔 `tsc` 를 돌린 뒤 **결과를 확인하지 않고 끝냈다.**

프롬프트로 두 번 우회했지만 뿌리는 아키텍처였다 — **verify 게이트가 test 만 봤다.**
lint·타입 실패는 그래프의 `verify` 노드에 도달하지 못했고, 따라서 retry 엣지가
그 실패에 반응할 수 없었다.

**수정** — `detectCheckCommand()` 를 추가해 verify 가 `check`·`typecheck`·`lint` 를
**test 앞의 게이트로** 돌린다. 실패하면 `verify: fail` 이고 "다시 구현" 엣지가 돈다.
타입 오류가 재시도 대상이 됐다.

### F5 — 재시도가 실패 이유를 모른 채 돈다

retry 엣지는 도는데 에이전트는 **같은 프롬프트를 다시** 받았다. steering 은 턴 경계에서
주입되므로 재진입 첫 호출이 못 본다. 그래서 실패 출력의 오류 줄을 추려
`<verify_feedback>` 으로 프롬프트 자체에 싣는다.

F4+F5 이후 A 태스크가 **처음으로 초록**이 됐다 — 4파일 · 203 테스트 · lint·타입 통과.

### F6 — 심볼릭 링크로 샌드박스를 벗어난다 (보안)

**가장 중요한 발견.** dogfooding 도중 **원본 저장소의 파일이 수정됐다.**

`safePath()` 는 문자열만 검사했다. 에이전트가 쓴 경로는 cwd 안이었지만
(`node_modules/@xcode/sdk/src/events.ts`), `node_modules` 가 원본을 가리키는
심링크여서 실제 쓰기는 밖에서 일어났다. 워크스페이스 링크가 상대 경로
(`../../packages/sdk`)라 사본에서도 원본으로 이어졌다.

이건 dogfood 하네스만의 문제가 아니다 — **심링크가 있는 모든 저장소에서 성립한다.**
node_modules · 모노레포 · dotfiles 어디서든.

**수정 두 겹**
1. `safePath` 가 존재하는 조상까지 `realpath` 로 정규화한 뒤 다시 검사한다.
   아직 없는 경로(write 가 만들 파일)도 조상 기준으로 막는다.
2. dogfood 는 node_modules 를 **복사**하고 워크스페이스 링크를 사본으로 다시 건다.

회귀 테스트 5건 — 링크로 덮어쓰기 · 링크 안 새 파일 · edit 경로 · 정상 경로 통과
(과잉 차단 아님) · cwd 안을 가리키는 링크 허용.

**들어온 변경은 원복했다.** 코드 자체는 정확했고 검사도 통과했지만, 승인 없이 들어온
것을 남기지 않는다. 격리를 고친 뒤 재실행해 사본 209 · 원본 208 로 유출 0 을 확인했다.

## 3~4주차 — 프로바이더 확대

### 먼저 정정

"프로바이더 3종"은 **구현 파일 수**였다. 실제로는 4종이 배선돼 있었다 —
anthropic · openai · deepseek · ollama (뒤 셋은 `OpenAiCompatProvider` 공용).
진짜 빈칸은 **Gemini**(API 형태가 다름)와 **OAuth** 였다.

### Gemini (`GoogleProvider`)

OpenAI 호환이 아니라 세 군데가 다르다:

| | OpenAI | Gemini |
|---|---|---|
| 메시지 | `messages[{role, content}]` | `contents[{role, parts[]}]` · role 은 user/model 뿐 |
| system | 메시지의 한 역할 | **별도 필드** (`systemInstruction`) |
| 툴 | `tools[]` 평면 | `tools[{functionDeclarations[]}]` 한 겹 더 |
| 툴 결과 | `role: tool` + id | **user 차례의 `functionResponse` part · id 없음** |
| 스트림 | 델타 조각을 합쳐야 함 | 한 줄이 완결된 JSON |

**id 가 없는 것**이 가장 성가셨다. 우리는 `toolUseId` 로 짝을 맞추므로 보낼 때
이름으로 되돌리고, 받을 때 `gemini_<n>_<name>` 형태로 우리가 만들어 붙인다.

구현하며 잡은 함정 셋:
- **함수 호출로 끝나도 `finishReason: STOP`** 이 온다. 그대로 넘기면 agent loop 가
  "할 일 끝"으로 읽고 툴을 실행하지 않는다 → 호출을 봤으면 `toolUse` 로 바꾼다.
- **스키마 방언이 부분집합**이다. `additionalProperties` 를 보내면 400 이 난다 → 걸러낸다.
- **키를 URL 쿼리에 넣지 않는다.** 로그·프록시·셸 히스토리에 그대로 남는다 →
  `x-goog-api-key` 헤더로. 테스트가 이걸 지킨다.

테스트 10건 — OpenAI 호환과 **다른 부분만**. 같은 부분은 `openai-compat` 이 이미 덮는다.

### `--list-models`

모델 id 를 외우게 하지 않는다. **키가 있는 프로바이더의 것만** 보여준다 —
쓸 수 없는 모델을 나열하면 목록이 거짓말이 된다.

```
deepseek-v4-pro    deepseek     64k
deepseek-v4-flash  deepseek     64k
qwen3-coder:30b    ollama      128k

기본 선택: deepseek-v4-pro
```

### 미룬 것

- **Anthropic OAuth** — 구독자(Pro/Max)가 API 키 없이 쓰는 경로. device flow ·
  토큰 갱신 · 저장이 필요하고 **본질적으로 대화형**인데 우리는 TUI 를 걷어냈다.
  호스트 연동(7~8주차)과 함께 다루는 것이 맞다.
- **ollama live 검증** — 배선은 돼 있으나 데몬이 없어 실측 못 했다. 남은 관찰.

### 검증

- 테스트 **221 통과** · 벤치 **33/33** · 기준선 대비 변화 없음.
- 프로바이더 **4 구현 / 8 모델** (anthropic · openai · google · deepseek · ollama).

## 4주차 — 툴 보강

### 진단이 예상을 뒤집었다

「`edit` 가 큰 파일에서 `oldText` 유일성 때문에 고생한다」고 예상하고 시작했다.
dogfood 세션 전체를 뒤져보니 **57건 전부가 "찾지 못했다"였고 유일성 실패는 0건**이었다.

실패 입력을 열어보니 원인이 하나였다:

```
에이전트가 보낸 것          실제 파일
export interface RunSummary {   export interface RunSummary {
    turns: number;                turns: number;      ← 2칸
```

`read` 가 붙이는 `%6d␣␣` 접두사를 벗길 때 정렬이 어긋난 것이다.

### F7 — edit 가 들여쓰기 차이를 못 넘는다

**수정** — 정확히 못 찾으면 **줄마다 앞 공백만 무시하고** 다시 찾는다.
내용은 글자 하나도 봐주지 않는다 — 들여쓰기는 도구가 만든 잡음이고 내용 불일치는
진짜 불일치다. 유일할 때만 적용하고, **파일의 원래 들여쓰기를 보존**한다.

단순한 델타 덧셈으로는 안 됐다. 실측 데이터가 `[0,4,4]` vs `[0,2,2]` 였다 —
균일하게 밀린 게 아니라 **들여쓰기 폭이 다른** 것이라 첫 줄 기준 델타는 0 이 나온다.
그래서 매치된 블록에서 **want→actual 대응표**를 뽑아 쓴다. 추측이 아니라 관측이다.

### F8 — 스크러버가 코드를 망가뜨린다 (보안 기능의 오탐)

F7 수정 후 실패가 57 → 3 으로 줄었는데, 남은 3건의 `oldText` 가 이랬다:

```
state.contextTokens = [REDACTED:assignment];
```

**우리 스크러버가 `contextTokens` 를 시크릿으로 오인했다** — 이름에 `TOKEN` 이
들어 있다는 이유로. 에이전트는 가려진 텍스트를 그대로 `oldText` 로 썼고 당연히 실패했다.
더 나쁜 것은 **코드에 대한 인식 자체가 틀어졌다**는 점이다.

`tokenCount` · `accessKeyId` · `refreshToken` 을 쓰는 **모든 코드베이스**에서 성립한다.

**수정** — 값이 코드처럼 생겼으면(괄호·연산자·점) 가리지 않는다.
미탐이 조금 늘더라도 코드를 망가뜨리는 오탐이 훨씬 비싸고, 진짜 자격 증명은
접두사 규칙(`sk-` · `ghp_` · `AKIA…`)이 이미 잡는다.
벤치 `secret` 태스크 2/2 로 **차단은 그대로**임을 확인했다.

### F9 — 사람이 무엇이 바뀌었는지 못 본다

CLI 는 `✓ edit: 수정함 cart.js (+10 −10)` 한 줄만 찍었다. 두 가지가 잘못이다 —
**무엇이** 바뀌었는지 안 보이고, 저 숫자마저 거짓이다(블록 줄 수를 그대로 셌다.
10줄 블록에서 1줄만 고쳐도 `+10 −10`).

**수정** — 줄 단위 diff 를 붙였다. 설계에서 하나만 고르라면 이것이다:

> **diff 는 `details` 로만 나가고 툴 결과 `content` 에는 들어가지 않는다.**

에이전트는 자기가 방금 뭘 썼는지 안다. diff 를 본문에 넣으면 컨텍스트만 두 배로 먹고
아무것도 알려주지 않는다. diff 는 **사람의 검토 표면**이지 모델의 입력이 아니다.

```
  ✓ edit: 수정함 cart.js (+1 −1)
  −     sum += item.price;
  +     sum += item.price * item.qty;
```

대용량 대비 세 겹 — 변경 없는 구간 접기(`⋯ N줄`) · 전체 24줄 상한 ·
한 줄 160자 상한(미니파이된 파일 하나가 화면을 덮지 못하게). LCS 는 공통 접두/접미를
먼저 잘라내고, 그래도 640k 셀을 넘으면 "통째 교체"로 정직하게 떨어진다 —
조용히 오래 걸리는 것보다 낫다.

### 실측

| | edit 실패 |
|---|---|
| 수정 전 | **57건** (전부 "찾지 못했다") |
| F7 후 | 3건 (전부 스크러버 오탐) |
| F7+F8 후 | **0건** |

같은 태스크를 세 번 돌려 잰 값이다.

벤치 n=3 (33 시도) — **완료율 100% · 검증 100% · 개입 0.12회 · secret 노출 0건**,
기준선 대비 **변화 없음**. 툴을 건드렸는데 회귀가 없다는 것이 확인할 값이었다.

## 5주차 — 슬래시 명령 · 세션 선택

### 슬래시 명령 = 저장소가 소유하는 프롬프트

`.xcode/commands/review.md` 를 두면 팀 전원이 `xcode "/review src/auth.ts"` 로 **같은**
리뷰를 돌린다. 워크플로가 각자 머릿속이 아니라 버전 관리되는 파일에 있다 —
이것이 "정책 계층"이라는 말의 실물이다.

프론트매터는 `description` 하나만 읽는다. `model` · `approve` 를 넣고 싶어지지만
그건 **저장소 파일이 자기 권한과 비용을 정하는** 꼴이다. 신뢰 결정은 사람이 CLI 에서 한다.

### 이 기능이 우리 게이트의 결함을 드러냈다

명령 본문은 에이전트의 지시가 되므로 신뢰 게이트를 지나야 한다.
게이트가 이미 `.xcode/` 전체를 담당하니 부르기만 하면 될 줄 알았는데, 테스트가 통과하지 않았다.

| | |
|---|---|
| `requiresTrust()` | `.xcode/` 아래는 전부 검사 대상 |
| `discoverResources()` | **하드코딩된 3개 디렉터리만** 훑음 |

`.xcode/commands/` 만 있는 저장소는 "승인할 것이 없다"로 읽혀 **자동 승인**됐다.
게이트가 자기를 연 것이다. 리소스를 추가할 때마다 조용히 재발하는 종류라,
목록 대조를 버리고 **디스크를 직접 훑도록** 바꿨다 — 두 함수가 같은 규칙을 쓴다.

회귀 테스트는 **아직 존재하지 않는 이름**(`.xcode/hooks-that-do-not-exist-yet`)으로 건다.

### 세션 선택

`--resume` 이 파일 경로만 받았다. 실제 사용법은 `ls ~/.xcode/agent/sessions/…` 를
먼저 치는 것이었다 — 그건 도구가 할 일이다.

```
 1    2분 전  5엔트리
      다음 파일이 커밋할 준비가 됐는지 보라: billing.js …
      ↳ 문제 없다.
```

`--sessions` 목록 · `--resume 2` 번호 · 값 없이 주면 TTY 에서 물어본다.
비대화형에서 조용히 "가장 최근 것"을 고르지 않는다 — 그건 `-c` 가 하는 일이고,
사람이 고르려던 자리에서 도구가 대신 고르면 엉뚱한 세션에 작업이 쌓인다.

함정이 하나 있었다. `xcode -r "계속해줘"` 가 프롬프트를 세션 id 로 먹고 도움말만 뱉었다.
이제 **세션 참조처럼 생긴 값**(숫자 · 경로)만 삼킨다.

### 새 기능으로 새 기능을 리뷰했다

만든 `/review` 를 dogfood 에 그대로 걸었다. 6건 중 4건이 실물이었다:

| 지적 | 판정 |
|---|---|
| `/commands` 가 게이트를 안 지난다 | **맞다** — 목록 경로는 게이트를 아예 안 불렀다 |
| 읽고 나서 검사한다 | **맞다** — 막아도 내용은 이미 메모리에 있었다 |
| 심링크로 프로젝트 밖을 읽는다 | **기전은 틀렸다** (`path.resolve` 는 심링크를 풀지 않는다). 다만 승인된 프로젝트에서는 실제 위험이라 realpath 봉쇄를 넣었다 |
| `Math.round` 가 경과 시간을 부풀린다 | "항상 크게"는 틀렸지만 방향은 맞다 — `floor` 가 옳다 |
| UTF-16 vs 바이트 혼동 | 상한 이름이 부정확한 정도. 다만 **확인하다 더 나쁜 것을 찾았다** ↓ |

마지막 것을 확인하다 발견한 진짜 결함: 스캔 창을 **문자 오프셋**으로 잘라서
잘린 자리의 줄이 항상 깨졌다. 큰 세션마다 `! 읽지 못한 줄 1개` 가 떴다 —
**손상 카운터가 도구 자신이 만든 잡음을 손상이라고 보고**하고 있었다.
그 숫자가 잡음이면 아무도 안 믿는다. 줄 단위로 자르도록 고쳤다.

### 백틱 함정을 규칙으로 바꿨다

`HELP` 는 템플릿 리터럴이라 안에 백틱을 넣으면 문자열이 거기서 끝난다. 두 번 당했다.
tsc 는 "구문 오류" 위치만 알려줄 뿐 원인을 말해주지 않는다.
check.sh 에 규칙을 넣되 **biome·tsc 보다 먼저** 돌게 뒀다 —
구문이 깨지면 tsc 가 먼저 죽어서 설명하는 검사에 닿지 못하기 때문이다.
(처음엔 뒤에 뒀다가, 함정을 심어 확인해보고 옮겼다.)

## 6주차 — 릴리스 · CI

### 가장 중요한 발견: 설치본이 아예 돌지 않았다

배포 준비를 시작하며 제일 먼저 한 것은 실제로 설치해보는 것이었다.

```
Error [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
  Stripping types is currently unsupported for files under node_modules
```

**Node 는 `node_modules` 아래에서 타입 스트리핑을 거부한다.**
저장소 안에서는 268개 테스트가 전부 초록인데, `npm i -g` 한 순간 첫 import 에서 죽는다.

> 저장소 안의 초록은 배포 가능을 뜻하지 않는다.

이건 테스트로 잡히지 않는 종류다. 테스트는 저장소 안에서 도니까.
잡는 방법은 하나뿐이다 — **진짜로 설치해서 실행해보는 것.**

### 개발 경로와 배포 경로를 나눴다

| | 진입점 | 이유 |
|---|---|---|
| 개발 | `src/index.ts` | 빌드 없이 바로 실행 |
| 배포 | `dist/index.js` | Node 가 node_modules 아래 `.ts` 를 못 읽는다 |

`publishConfig.exports` 로 될 것 같았는데 **`npm pack` 에서 적용되지 않았다.**
확인할 수 없는 동작에 릴리스를 걸지 않는다 — `scripts/pkg-entry.mjs` 가 명시적으로 바꾸고,
`release.sh` 가 `trap` 으로 반드시 되돌린다. 되돌리지 못한 상태는 테스트가 잡는다.

부수적으로 나온 것 둘:
- `rewriteRelativeImportExtensions` 는 **JS emit 에만** 적용된다.
  선언 파일은 `.ts` 를 그대로 유지해서, 설치본의 타입 해석이 깨진다. → 빌드에서 정리한다.
- 산출물에 `.ts` import 가 남으면 빌드가 실패한다. 조용히 넘어가면 설치본에서 죽는다.

### 릴리스가 스스로를 검증한다

`release.sh` 는 **워크스페이스 심링크가 없는 빈 디렉터리**에 tarball 만으로 설치하고 확인한다:

```
▸ 설치 검증 (워크스페이스 밖, tarball 만)
  ✓ xcode --version → xcode 0.1.0
  ✓ SDK 임베드 · 스크러버 동작
  ✓ 조회 명령 동작 (세션 없음)
```

스크러버까지 확인하는 이유 — 보안 장치가 개발 환경에서만 붙어 있으면 최악이다.

### CI

| 잡 | 하는 일 |
|---|---|
| `check` | lint · 타입 · 구조 규칙 · 테스트 (ubuntu) |
| `install` | **빌드 → 패키징 → 실제 설치 실행** (ubuntu · macOS) |
| `dogfood` | 키가 있을 때만. 포크 PR 에는 시크릿이 없다 |

`install` 잡이 이 CI 의 존재 이유다. 이걸 빼면 위 사실을 다시 잊는다.

### CI 를 쓰기 전에 CI 가 잡을 것을 잡았다

리눅스에서 죽었을 것들을 미리 고쳤다 —

- `sed -i ''` 는 **BSD 문법**이다. GNU sed 에서 죽는다.
- `shasum` 대신 `sha1sum` 인 환경이 있다. 있는 것을 골라 쓴다.
- `find -type f -name A -o -name B` 는 `(-type f -a A) -o B` 로 묶인다.
  `dist/*.d.ts` 가 들어오면서 **빌드 산출물이 "바뀐 소스"로 잡힐 뻔했다.**

### 배포 준비를 코드로 지킨다

`packaging.test.ts` — 버전이 한 곳에서만 오는가 · `files` 에 `dist` 가 있는가 ·
개발 진입점이 원상태인가 · 산출물에 `.ts` import 가 없는가 ·
**런타임 의존성이 우리 패키지뿐인가.**

마지막 것이 특히 그렇다. "의존성 0개"는 우리 주장이고, 주장은 검사로 지킨다.

### 벤치가 ✗ 를 냈고, 고치지 않았다

6주차 회귀 확인에서 두 번 연속 "안정성 100%" 기준에 미달했다.

| 실행 | 실패 | 완료율 |
|---|---|---|
| 1차 | `multifile` 2/3 | 32/33 |
| 2차 | `readme` 2/3 | 32/33 |

**매번 다른 태스크가 실패했다.** 6주차 변경은 전부 빌드 시점(빌드·패키징·CI·문서)이고
에이전트 실행 경로를 건드리지 않았다. `multifile` 단독 재실행은 3/3 이었다.

`readme` 실패 사유는 "setup 절 제목이 없다"였다. 검사기가 어휘를 보고 있어서
`## Getting Started` 같은 제목을 놓치는 것 아닌가 의심했는데 —
**4회 재현 시도에서 4회 모두 `## Setup` 이 나왔다. 가설이 틀렸다.**
근거 없이 검사기를 느슨하게 하지 않았다. 초록으로 만들려고 검사를 약화시키는 것은
우리가 `/review` 에서 스스로 경계하라고 적어둔 "거짓 요약"과 같은 종류다.

남는 사실은 이것이다 — **모델 변동이 약 1/33 수준으로 존재하고, 벤치의
"전회 통과 100%" 기준은 그것을 회귀와 구분하지 못한다.** 기준을 낮추지 않았다.
회귀와 흔들림을 나누려면 `--compare` 가 미달 태스크만 자동 재실행해야 한다 —
7~8주차 후보로 남긴다.

### 남은 것

- 리눅스 경로는 **CI 첫 실행에서 확인해야 한다.** 이 기계에 Docker 가 없어 직접 못 돌렸다.
  위 세 가지를 미리 고쳤지만 검증은 아니다.
- `engines: >=23.6.0` 은 개발(타입 스트리핑) 기준이다. 배포본은 더 낮은 Node 에서도
  돌 가능성이 높지만 **실제로 돌려보지 않았으므로 낮추지 않았다.**

## 7–8주차 — 호스트 연동

TUI 를 직접 만들지 않기로 한 결정이 여기서 값을 내야 한다.
pi 는 TUI 에 12,189줄을 썼다. 우리는 대신 **`--json` 스트림을 계약으로 만들고**
그 위에 기존 IDE 를 얹는다. 그러면 프로토콜이 곧 제품 표면이다.

### 계약에 없던 세 가지

프로토콜은 이미 있었다. 없던 것은 계약이 되기 위한 조건들이었다.

**① 버전.** 호스트가 무엇과 말하는지 알 방법이 없었다. 이제 첫 줄은 항상 handshake 다:

```json
{"type":"protocol","version":1,"agent":"0.1.0","events":[...40종],"commands":[...5종]}
```

목록을 스트림 안에 실은 이유 — **호스트가 문서를 따로 믿게 하지 않는다.**

**② 모든 명령에 응답.** 전에는 **거절만** 보냈다. `gate` 를 보낸 호스트는 먹혔는지
알 수 없어서, UI 가 낙관적으로 "승인됨"을 그려놓고 실제로는 안 먹은 상태가 될 수 있었다.
`id` 로 짝을 짓고, JSON 파싱이 실패한 줄에도 응답한다 — 무응답은 호스트를 영원히 기다리게 만든다.

**③ 끝 신호.** ↓ 아래 참조. 문서를 쓰다가 찾았다.

### 계약 테스트가 즉시 값을 냈다

목록은 손으로 적을 수밖에 없다 (타입은 런타임에 사라진다).
그래서 테스트가 **소스의 유니온을 읽어 대조한다.** 처음 돌린 순간 잡힌 것:

| | |
|---|---|
| 선언에 없던 실제 이벤트 | `session_restored` · `files_rolled_back` · `agent_settled` |
| 실제로 없는데 선언한 것 | `compaction_stage` · `checkpoint_written` · `rollback_result` |

내가 손으로 적은 목록의 **6항목이 틀렸다.** 호스트가 이 목록을 믿었다면
세 이벤트를 영원히 못 봤고, 세 개는 오지 않을 이벤트를 기다렸다.

`XcodeEvent` 가 **두 패키지에 걸친 유니온**(`AgentEvent` | `HarnessEvent`)이라
한쪽만 읽어서 처음엔 목록 전체가 어긋난 것처럼 나오기도 했다.

### 문서를 검증하다 진짜 결함을 찾았다

문서에 "`run_summary` 가 항상 마지막 이벤트다"라고 적고, 확인해봤다:

```
이벤트 순서: [protocol, session_start, node_enter, classify_result,
              node_exit, workflow_edge, node_enter, research_start, research_done]
exit=1
```

**사실이 아니었다.** 프로바이더 호출이 실패하면 예외가 그대로 나가고
stderr 에 사람용 한 줄만 찍혔다. stdout JSONL 만 읽는 호스트에게는
**스트림이 그냥 멈춘 것**으로 보인다 — 끝났는지 죽었는지 알 수 없다.

정책 계층 결함 유형 A 그대로다: 장치(에러 표시)는 있는데 그 경계에서 아무도 부르지 않았다.
이제 json 모드는 죽을 때 `{"type":"error","fatal":true}` 를 내보내고,
레퍼런스 호스트는 **끝 신호 없이 끊긴 스트림을 실패로 본다.**

### 레퍼런스 호스트 — 결정의 실물

[`examples/host/host.mjs`](../impl/examples/host/host.mjs), 200줄, 의존성 0개.
xcode 를 import 하지 않는다 — 프로세스 경계만 쓴다. 어떤 언어로든 번역 가능하다.

실측으로 확인한 세 경로:

| 경로 | 결과 |
|---|---|
| 게이트 거부 | `분류: complex / 위험 high` → 호스트가 거부 → `stopReason: human_gate`, exit 3 |
| 게이트 승인 | 호스트가 승인 → 실행 이어짐 → `검증: pass` |
| 실행 중 스티어링 | 호스트가 `"Hi 가 아니라 Hello"` → 파일이 `"Hello "` 로 바뀜 |

세 번째가 특히 그렇다. 에이전트는 그 지시를 프롬프트에서 받지 않았다 —
**실행 중에 호스트가 끼워넣었고 다음 턴에 반영됐다.**

호스트를 쓰면서 내 코드에서도 결함이 하나 나왔다:
`argv.indexOf("--steer")` 가 -1 일 때 `steerAt + 1` 이 0 이 되어 **첫 인자가 잘려나갔다.**
센티널을 산술에 그대로 넣으면 이렇게 된다.

### 계약을 코드로 지킨다

- `protocol-contract.test.ts` — 목록이 소스와 정확히 같은가 · 버전 변경은 의도적인가
- `protocol-wire.test.ts` — **모델도 네트워크도 없이** end-to-end 4건:
  첫 줄이 handshake 인가 · 나간 이벤트가 전부 선언됐는가 ·
  보낸 명령마다 응답이 오는가 · 호스트 승인으로 실행이 이어지는가 · 죽어도 끝을 알리는가
- CI 에 호스트 스모크 추가 (handshake 수신)

CI 스모크를 쓰면서도 하나 밟았다 — `| head -1` 로 확인하면 SIGPIPE 로 상류가 죽고
`pipefail` 이 실패로 읽는다. 파일로 받는 쪽이 파이프 요령보다 결정적이다.

### in-process 도 같은 것이다

```js
session.on((event) => renderInYourUi(event));   // --json 이벤트와 동일
session.resolveGate("approve");                 // --json 명령과 동일
```

`--json` 은 이것을 프로세스 경계 너머로 옮긴 것뿐이다.
`run()` 에 `input` 스트림을 뚫은 것도 그래서다 — 테스트용 구멍이 아니라
프로세스를 띄우지 않는 호스트(Tauri 사이드카 · IDE 확장)가 쓰는 자리다.

### 안 한 것: Anthropic OAuth

3~4주차에 여기로 미뤄뒀는데 **하지 않았다.** 미룬 이유가 해소되지 않았고,
새 이유가 하나 더 생겼다.

- 구독 로그인 흐름(엔드포인트 · 클라이언트 id · device code 규약)을 **여기서 검증할 수 없다.**
  구독 자격 증명이 없고, 키를 대화에 붙여넣지 않는다는 원칙도 그대로다.
- 검증 못 하는 OAuth 코드를 넣는 것은 이 프로젝트에서 계속 피해온 것과 같은 종류다 —
  **확인할 수 없는 동작에 기능을 거는 일.** 릴리스에서 `publishConfig.exports` 를
  버린 것과 같은 판단이다.

지금 상태로도 구독자가 못 쓰는 것은 아니다. `ANTHROPIC_API_KEY` 로 동작하고,
호스트가 자기 인증을 가진 경우 `--json` 위에서 그 호스트가 처리한다.
필요해지면 그때, **실제 구독 계정으로 왕복을 확인할 수 있는 환경에서** 넣는 것이 맞다.
