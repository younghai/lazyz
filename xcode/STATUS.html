목표

무엇을 만드는가

개발자가 자연어로 코딩 태스크를 주면 계획 → 실행 → 검증까지 끝내는 agent-native 코딩 하네스. 기존 도구는 짧은 대화엔 강하지만 길어지면 컨텍스트를 잃고 중간에 멈춘다. 그 지점을 정면으로 겨냥한다.

기반 모델은 pi-coding-agent. 4-package 구조, JSONL 세션 트리, 이벤트 기반 루프, minimal core + aggressive extensibility 철학을 그대로 계승한다.

차별점 셋

진짜 Agent Loop

한 번 답하고 끝나는 게 아니라, 툴을 쥐고 결과를 확인하며 일이 끝날 때까지 스스로 반복한다.

계층형 Compaction

중복 제거 → 절단 → 도구 인식 축약 → 요약 → 하드캡. 값싼 무손실부터 시작해 필요할 때만 비싼 요약으로 간다.

Dynamic Workflow

실패하면 되돌리고, 컨텍스트가 차면 압축으로 빠지고, 위험하면 사람에게 넘긴다. 고정 파이프라인이 아니다.

  • 2026-07-27 — 완료 워크플로 그래프 — 빠져 있던 retry 엣지

    session.ts 의 if/else 를 노드·엣지 데이터로 뺐다. 엔진은 xcode 를 모르고 "어떤 결과면 어디로"만 안다 — 사용자가 자기 그래프를 줄 수 있는 이유다. 그리고 원안이 요구한 "검증 실패 → 다시 구현"이 구현에 통째로 빠져 있던 것을 채웠다. 위에서 아래로 흐르는 구조에는 되돌아가는 엣지를 넣을 자리가 없었기 때문이다. 예산 가드 · maxSteps · 턴 캡으로 무한 루프를 세 겹으로 막는다.

  • 2026-07-27 — 완료 컴팩션 조사자 — 요약을 agent loop 로

    원안 그대로: "compaction 도 하나의 agent loop 로 만든다." 조사자가 log_outline·log_grep·log_read 로 기록을 뒤진 뒤 요약을 쓴다. 조사 범위는 전체, 대체 범위는 머리뿐(replaceUpTo) — 이걸 분리하지 않으면 조사자가 "이 기록은 현재 목표와 무관하다"고 단정한다 (근거는 유지 구간에 있는데). 실측: 현재 과업 집중도 0.11 → 0.67, 유지 구간의 JOIN 실패 이력을 찾아내 재발 방지 게이트로 승격했다. 단일 호출로는 원리적으로 불가능한 결과다 — 그 정보가 창 밖에 있기 때문이다.

프로토타입이 확정한 스펙 3건

1. 컴팩션 결합 방식 — 파이프라인 4단계가 “무엇을 줄일지”, cut point / firstKeptEntryId / retainedTail 이 “어디서 자를지”를 정한다. 두 설계는 배타적이지 않았다.

2. 세션 엔트리 스키마 — 상세설계서의 10종 / parentId 를 정본으로 채택(API설계서의 5종 / parent 안은 폐기).

3. 워킹 메모리 안전장치 — checksum 동일성이 아니라 보호 필드 단조성. decisions[] 가 자라기 때문에 checksum 은 애초에 성립하지 않는다.

테스트가 실제로 잡은 것

구현 중 테스트가 잡아낸 결함 셋. 셋 다 조용히 넘어갔으면 나중에 훨씬 비쌌을 것들이다.

  • 1 사용자 프롬프트가 세션에 저장되지 않던 버그. agentLoop 이 user 메시지를 배열에만 넣고 message_end 를 내지 않아 영속화 구독자가 원 요청을 못 봤다. --continue 로 이어 열면 에이전트가 목표를 잃는 상태였다.
  • 2 요약이 컨텍스트를 늘리던 경우. 요약 대상 구간이 작으면 요약본이 원본보다 커진다. MIN_SUMMARIZE_TOKENS 아래는 요약하지 않도록 막았다.
  • 3 테스트 카운트 파싱 누락. "3 failed | 21 passed" 를 통과로 오인했다. exit code 만 믿으면 나는 사고다.

추가로, 구현 과정에서 프로토타입에서는 보이지 않던 설계 문제가 하나 드러났다 — 컴팩션 단계별 적용 구간을 나누지 않으면 2단계(절단)가 4단계(요약)의 재료를 먼저 지워버린다. 요약 구간 / 유지 구간 / 최신 턴 셋으로 분리해 해결했다.

에이전트 간 결과 전달 — in-process → 파일 → HTTP → 큐. 지금은 함수 호출 하나뿐이고 프로토콜이 없다. 원안의 마지막 빈칸.

03비용 미표시
usage 미사용

agent.usage 는 모으는데 아무도 안 쓴다. 컨텍스트 경제학이 피치인 제품이 지출을 안 보여주는 건 앞뒤가 안 맞는다.

04세션 트리 UI
분기 · 클론

「이어서 열기」는 최근 세션만 연다. 프로토타입 View 4 가 보여준 분기점 선택과 fork/clone 은 아직 화면이 없다.

알려진 격차

  • ○ 세션 목록 UI 없음. 「이어서 열기」는 가장 최근 세션만 연다. 여러 세션 중에서 고르거나 분기점을 보는 화면은 프로토타입에만 있다.
  • ○ 워킹 메모리를 에이전트가 직접 쓰지는 않는다. 실행 결과와 컴팩션 요약에서 자동으로 만들어진다. 턴 중간에 에이전트가 스스로 결정을 적는 경로는 아직 없다.
  • ○ 완료 기준 미측정. 「샘플 태스크 10개 중 7개 이상」 같은 지표는 live 모델이 붙어야 잴 수 있다. 지금은 재는 장치가 없다.

Live 검증 결과 — 2026-07-26

DeepSeek v4-flash · v4-pro 양쪽에서 전 경로 통과. 실제 모델이 코드베이스를 읽고, 버그를 고치고, 테스트를 실행해 통과시켰다. v4-pro 는 greet(name) 의 파라미터를 보존한 정확한 수정을 했다.

Mock 만으로는 절대 드러나지 않았을 결함 3건을 여기서 잡았다. ① 잘못된 모델 id 로 400 이 났는데 classify 가 조용히 삼키고 진행 — 원인이 세 단계 뒤에야 드러났다. ② DeepSeek v4 는 둘 다 reasoning 모델이라 응답 전에 사고 토큰을 쏟는데, 구조화 출력 호출의 maxTokens 를 300 으로 잡아 사고가 예산을 다 먹고 JSON 이 잘렸다. 짧게 생각한 날은 통과해서 간헐적으로만 실패했다. ③ 프로바이더 오류가 원시 스택으로 노출됐다.

재현: ./scripts/live-check.sh deepseek-v4-pro — 격리된 임시 프로젝트에서 실제 모델이 버그를 고치는지 자동 판정한다. 사용자 저장소는 건드리지 않는다.
